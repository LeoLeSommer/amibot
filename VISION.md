# Amibot — Statement of Intent

> This document states the intent behind Amibot, not its implemented state. The
> current repository is a skeleton described in [`README.md`](README.md);
> working conventions live in [`AGENTS.md`](AGENTS.md). Do not assume the
> module names, crates, or directory layout below already exist. The technology
> list and repository structure are indicative and must be reconciled with the
> actual repository before they are relied on.

## 1. Vision

Amibot is an open-source platform for interacting with AI agents, designed to be
modular, extensible, and customizable. It should be able to become a different
application depending on the modules installed on its backend.

The fundamental idea is to avoid building a monolith with every feature baked
in. Instead, Amibot provides:

- a minimal core (`amibot_core`);
- independent modules that add functionality;
- an extension system that lets the community develop its own modules;
- clients that build their interface dynamically from the modules available on
  the server.

The same Amibot client could therefore become a very different application
depending on the backend it connects to. Modularity is a central architectural
principle of the project.

## 2. General architecture

### Amibot Core

`amibot_core` is the heart of the system. It must not contain business features
such as chat, user accounts, or conversations. It provides only the mechanisms
needed to run the platform:

- Module Registry: registration of modules.
- Module Loader: loading of modules.
- Module Lifecycle: activation, deactivation, installation, uninstallation.
- Dependency Resolver: management of dependencies between modules.
- Capability Registry: registration of exposed capabilities.
- UI Contribution Registry: registration of interface contributions.
- Manifest API: description of the application and its available features.
- Permissions: authorization management.
- Events: communication between modules.

The core must remain as independent as possible from the official modules. A
community module must be treated exactly like an official one.

### Official modules

The main features are provided by independent modules. The first envisioned
modules are:

#### `amibot_chat`

- Interaction with an AI agent.
- Sending and receiving messages.
- Streaming responses.
- Handling tool calls.
- A2UI integration to render dynamic interfaces generated by agents.

#### `amibot_identity`

- User management.
- Registration and authentication.
- Login and logout.
- Account management and user-bound authorizations.

#### `amibot_session`

- Conversation management.
- Creating and deleting conversations.
- Listing conversations.
- Persisting and restoring history.

Dependencies must stay loose. For example, `amibot_session` may depend on
`amibot_chat`, but `amibot_identity` should be optional: a user must be able to
hold conversations without necessarily owning an account.

### Distribution

A distinction must be made between core components and the modules shipped by
default. The intended approach:

- `amibot_core`: mandatory.
- `amibot_chat`, `amibot_identity`, `amibot_session`: independent official
  modules.
- `amibot_standard`: a distribution that provides the official modules and
  enables them by default.
- Community modules: installed separately.

No official module may receive special architectural privileges inside the
core.

## 3. How the client works

The Amibot client must be as universal as possible. It must not assume that the
backend necessarily has chat, authentication, or conversation history.

On connection, the client queries the server for its manifest, for example
`GET /api/v1/app/manifest`. The manifest describes:

- the core version;
- installed and enabled modules;
- available capabilities;
- UI contributions;
- any compatibility constraints.

The client uses this information to build its interface.

### Expected behavior

**No backend connected.** The application shows only settings and the
configuration needed to connect to an Amibot server.

**Backend connected, no module installed.** The application shows the server
settings and a page telling the user that no module is installed.

**Backend with `amibot_chat`.** The application shows a minimalist chatbot
interface, in the spirit of ChatGPT. The chat uses A2UI for dynamic interfaces
generated by agents.

**Backend with `amibot_identity`.** The application adds a hamburger menu, a
sidebar or navigation area, and a login and account-management interface.

**Backend with `amibot_session`.** The application adds a conversation list to
the sidebar.

These features must appear automatically when the corresponding modules are
enabled on the backend. The client should not need an update for each module
activation or deactivation, as long as the required components are already
available.

## 4. UI contribution system

This is a particularly important part of the project. Modules must be able to
contribute to the global interface without the core knowing their business
features.

To make this possible, the client exposes interface locations called `slots`,
for example:

- `app.header`
- `app.navigation`
- `app.sidebar`
- `app.settings`
- `chat.header`
- `chat.main`
- `chat.footer`

A module can declare that it wants to display a component in a particular slot.
The server aggregates these contributions and exposes them in the manifest. The
client then interprets the contributions and builds its interface.

The design must address:

- ordering of contributions;
- conflicts between contributions;
- dependencies between modules;
- required permissions;
- version compatibility;
- differences between platforms.

## 5. Community extensions and dynamic UI

A major goal of Amibot is to let the community build complete modules, including
their own interfaces.

A concrete example is Git. A module `amibot_git` could add repository
management, branch display, commit history, diffs, and Git operations. We do
not want to embed all of these components into the base Amibot application. We
also want to let the community build extensions for other version-control
tools such as Mercurial, Fossil, and others.

Two kinds of UI contributions are envisioned.

### A. Declarative UI

Extensions describe their interface as structured data. The client renders it
with a catalogue of generic components it already knows how to display, for
example buttons, forms, lists, tables, menus, panels, tabs, and layouts. This
approach is particularly valuable for compatibility across web, mobile, and
desktop.

### B. Embedded custom UI

Developers can provide their own frontend interface, potentially built with
React, Vue, Svelte, or other technologies. The client loads that interface in
an isolated environment, for example a sandboxed iframe on the web or a WebView
on mobile. The extension communicates with Amibot through a controlled API:

```ts
interface AmibotExtensionAPI {
  invoke(capability: string, args: unknown): Promise<unknown>;
  navigate(path: string): void;
  getContext(): Promise<ExtensionContext>;
}
```

Extensions must never be allowed to inject JavaScript freely into the main
application context. Security, isolation, permissions, and compatibility must
be considered from the outset.

Native features specific to macOS, Windows, Linux, iOS, or Android will always
require integration in the relevant client or an update to that client.

## 6. A2UI

A2UI is envisioned as a system that lets agents generate dynamic interfaces.
Two levels must be distinguished:

- the Amibot composition system determines the overall structure of the
  application and the contributions of extensions;
- A2UI generates dynamic interfaces inside surfaces controlled by Amibot.

A2UI must therefore not be responsible for the global composition of the
application.

## 7. Technical architecture (indicative)

Envisioned technologies:

- Backend core: Rust + Axum + Tokio.
- Agent runtime: TypeScript / Node.js.
- Mobile client: Expo + React Native.
- Web client: Expo Web / React Native Web.
- Desktop client: Tauri 2.
- Database: PostgreSQL.
- Communication: REST + SSE initially, WebSocket if needed.
- Monorepo: pnpm + Cargo.
- Deployment: Docker Compose.

Indicative structure:

```text
amibot/
├── apps/
│   ├── mobile/
│   ├── web/
│   ├── desktop/
│   ├── server/
│   └── agent-runtime/
├── packages/
│   ├── ui/
│   ├── ui-contracts/
│   ├── client-sdk/
│   ├── module-sdk/
│   ├── agent-sdk/
│   └── shared/
├── crates/
│   ├── amibot-core/
│   ├── amibot-modules/
│   ├── amibot-permissions/
│   └── amibot-storage/
├── modules/
│   ├── amibot-chat/
│   ├── amibot-identity/
│   └── amibot-session/
└── infrastructure/
```

This organization is indicative and must be confronted with the real repository
layout.

## 8. Architectural philosophy

1. The core must stay minimal.
2. Business features belong to modules.
3. Official and community modules must use the same mechanisms.
4. The backend is the source of truth for which modules are enabled.
5. The client builds its interface from the manifest.
6. UI contributions must be decoupled from backend features.
7. Extensions must not have free access to the application's internal context.
8. Permissions must be explicit and revocable.
9. The architecture must work across multiple platforms.
10. Avoid over-engineering: build incrementally while keeping the architecture
    extensible.

## 9. Development objective

The immediate objective is to build Amibot's foundations. The envisioned order
of development:

1. Build the core and its module system.
2. Build the manifest and its API.
3. Build the slot system and the client's component registry.
4. Let the client connect to a backend and compose its interface dynamically.
5. Develop `amibot_chat`.
6. Develop `amibot_identity`.
7. Develop `amibot_session`.
8. Design and publish the SDK for community module authors.
9. Add embedded custom UI contributions.
10. Build an extension catalogue.

This order may be adapted to the real state of the repository and to technical
dependencies.

## 10. Guidance

Before proposing or implementing a feature:

- Examine the repository and identify its current architecture.
- Consult the project documentation and conventions.
- Identify what already exists and what is missing.
- Do not reimplement an existing feature.
- Do not assume the examples in this document are existing code.
- Respect established technical choices when they are consistent with this
  vision.

Prefer incremental, modular, and testable development. When several
architectures are possible, state their trade-offs before choosing. Avoid
building complex features prematurely when they are not needed for the next
step.

The priority is to preserve Amibot's vision: a minimal core, independent
modules, and an interface that composes itself dynamically from the backend's
capabilities.
